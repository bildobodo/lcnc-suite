# Issue #35 Handoff: Event-Loop Stalls Around File Upload

## Context

GitHub issue #35 adds asyncio slow-callback instrumentation to investigate
`[HB-WAKE]` gaps. The first captured file-load event showed:

```text
[HB-WAKE] pre-send-to-pre-send gap 154ms (expected 33ms)
POST /upload 200 OK
Executing <Task WebSocketProtocol.run_asgi()> took 0.062s
Executing <Task WebSocketProtocol.run_asgi()> took 0.051s
```

The immediate safety budget is the HAL heartbeat watchdog: heartbeat edges
retrigger a 0.5 second `oneshot`. If the gateway event loop stalls long enough,
`oneshot.0.out` falls, the independent watchdog process drops `trip-latch`, and
the HAL chain drives LinuxCNC into latched ESTOP.

## Current Interpretation

The trace establishes event-loop starvation around upload and subsequent
WebSocket work. It does not yet prove that all 113ms of WebSocket callback time
is encoder GIL contention.

The `/upload` handler currently:

1. Reads the complete upload into memory.
2. Checks the size after the read.
3. Calls `atomic_write_bytes()` synchronously on the event-loop thread.

The slow-callback records identify the Uvicorn WebSocket task that held the
loop, but not the exact operation inside that task. The status envelope encoder
runs inline by deliberate design: an earlier dedicated-thread implementation
was measured and reverted because it added dispatch overhead without improving
storm-time latency.

The later generation-2 GC pauses are a separate, plausible contributor. They
do not explain the immediate upload-time stall unless a GC event is recorded at
the same time.

## Recommended Work

### 1. Move Atomic Writes Off The Event Loop

Run `atomic_write_bytes()` with `asyncio.to_thread()`.

This is a suitable thread offload because it is primarily filesystem I/O. It
preserves the existing temporary-file plus `os.replace()` atomicity while
allowing heartbeat and WebSocket tasks to run during the write.

Apply the same review to `/save` and other request handlers that invoke
synchronous persistence helpers from async code.

### 2. Stream Uploads With A Hard Size Bound

Do not materialize the entire allowed 50MB upload as one `bytes` object.

Read bounded chunks, count bytes while reading, write them to a temporary file,
reject immediately when the limit is exceeded, then atomically rename the
completed file. Clean up the temporary file on cancellation, validation
failure, or I/O error.

This reduces peak memory, large-object copying, allocation bursts, and delayed
generation-2 GC pressure.

### 3. Attribute The WebSocket Callback Time

Keep asyncio slow-callback logging and add narrow phase timings around:

- per-client status envelope construction
- tool metadata loading
- envelope encoding
- `ws.send_bytes()` / `ws.send_text()`
- any work performed immediately after upload or active-file change

The existing `ws.encode_slow` event should remain. Slow-callback debug mode may
be configuration-controlled after diagnosis because asyncio debug mode adds
runtime overhead.

### 4. Reduce Per-Client Fanout Work

The shared status body is already encoded once and inserted with `msgspec.Raw`,
but each client still builds and encodes its own envelope.

Preferred follow-up options:

- Broadcast one pre-encoded frame to clients with identical state.
- Move client-specific fields into a separate, lower-frequency message.
- Group clients by envelope variant and encode once per group.
- Coalesce status generations when fanout has not completed.
- Yield between bounded client batches so heartbeat execution is not starved.

Reducing duplicate work is preferable to moving the same Python work into more
threads.

### 5. Use Processes For Confirmed CPU-Bound Python Work

If profiling identifies a genuinely CPU-heavy Python transformation, use a
bounded subprocess or process pool. A process has its own interpreter and GIL.

The G-code preview parser already demonstrates the desired safety property:
expensive parsing happens in an isolated subprocess while the gateway event
loop continues servicing heartbeats.

Do not introduce an unbounded process queue, and ensure shutdown terminates or
cancels outstanding workers deterministically.

### 6. Evaluate GC Mitigation Separately

`gc.collect()` followed by `gc.freeze()` at stable startup may reduce
generation-2 scans of long-lived objects. It is not a direct fix for encoding
or upload I/O.

Adopt it only after confirming:

- slow generation-2 collections correlate with heartbeat delay
- resident memory remains stable
- cyclic garbage created after startup is still collected as expected
- startup and reconnect behavior are unaffected

The existing GC callback instrumentation provides the evidence needed for this
decision.

## Safety Invariants

Performance changes must preserve these properties:

1. The heartbeat remains generated by the gateway event loop whose health it
   measures.
2. A frozen or crashed gateway stops producing heartbeat edges.
3. `hal_watchdog.py`, `oneshot.0`, and `trip-latch` remain independent of the
   gateway process.
4. A watchdog trip produces a real, latched ESTOP.
5. Recovery still requires the existing operator reset path.
6. Worker queues and shutdown waits are bounded.
7. Upload publication remains atomic; LinuxCNC must never observe a partially
   written G-code file.

Do not move heartbeat generation to a helper process or dedicated native
thread. Doing so could keep the heartbeat alive while the command gateway is
unresponsive, masking the failure the watchdog is intended to detect.

Do not increase the 500ms watchdog timeout merely to accommodate application
latency. The goal is to restore execution margin, not weaken detection.

## Verification Plan

Measure before and after each change under the same workload:

- maximum permitted upload size
- repeated uploads and saves
- maximum expected visible-client fanout
- hidden/background browser tabs
- active LinuxCNC status polling
- preview refresh after file load

Record:

- maximum `[HB-WAKE]` gap
- asyncio slow-callback task and duration
- upload read/write duration
- per-client envelope encode and send time
- event-loop lag
- GC generation and duration
- RSS and worker queue depth

Acceptance criteria:

1. Upload and fanout do not produce unexplained callbacks over 50ms.
2. Normal worst-case operation retains substantial margin below the 500ms HAL
   watchdog threshold.
3. No partial upload is visible after cancellation or injected write failure.
4. A deliberately blocked gateway event loop still causes `oneshot.0.out` and
   `trip-latch` to fall, resulting in latched ESTOP.
5. Heartbeat recovery alone does not clear the latched trip.

## Suggested Order

1. Retain and refine the diagnostics.
2. Offload atomic upload/save writes.
3. Implement bounded streaming uploads.
4. Re-run the stress scenario and identify the exact WebSocket hot phase.
5. Reduce or group per-client envelope work.
6. Consider process isolation for any remaining confirmed CPU-bound work.
7. Evaluate `gc.freeze()` only from correlated GC evidence.
